# Pages publication status

Studio's admin sidebar polls `GET /api/admin/publication-status` every 30 seconds using normal authenticated requests. The endpoint requires administrator authorization and disables response caching. This is explicitly a site-wide view: a successful database save does not prove that item is included in Pages. The UI always states that new changes await publication and individual inclusion is unknown.

Mount only `<release-root>/.content-refresh` read-only at `/run/wp-publication` in the backend and set `WP_PUBLICATION_STATE_DIR=/run/wp-publication`. No release checkout, Docker socket, credentials, or snapshots are mounted. Reads are bounded to 64 KiB of `state.json`; absent, malformed, oversized or unreadable state returns unknown without disclosing paths or errors. No network calls or snapshot capture occur on API reads.

The refresh writer preserves existing phase/retry and frozen snapshot behavior. `running` and `started_at` mark an active attempt before capture; `updated_at` is the most recent transition. `completed_at` records successful verification after upload, while `checked_at` also advances for unchanged content whose public receipt matches. Neither receipt `built_at` nor a check timestamp is presented as a new publication. `failure` takes precedence over an old complete phase. Running state older than 60 minutes is marked stale; this is an inspection threshold, not automatic cancellation. Complete status whose latest check is absent or older than 60 minutes is visibly stale, while preserving the historical success. Future update timestamps return unknown. Symlinks and nonregular files are rejected. `deferred` means waiting for another run after content changed during build.

Complete status requires a matching `completed_key` and journal receipt. Legacy complete journals can show a verified previous publication without a completion timestamp. A normal code release without a refresh journal remains unknown. No per-item revision inclusion, scheduler liveness, current database comparison, or automatic retry is inferred. A hard interruption can leave running state; the next host run retains all existing locking and retry checks.
